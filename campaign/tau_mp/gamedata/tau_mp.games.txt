// 让单人战役的 tau cannon 拥有「多人模式」行为所需的两个代码位置。
// The two code locations needed to make the single-player campaign's tau cannon behave like "multiplayer mode".
//
// ── 适配的 server.dll 版本 ────────────────────────────────────────────────────
// ── Target server.dll versions
//   旧 build  md5 68278cc0c3a1e23d96c2b9d722ae7670   9,509,376 B
//             = F:/BMServer 死斗服用的那份（独立安装，不随 Steam 更新）
//   新 build  md5 421fee309fdc22f3dc7b5207a4810c3e   9,530,984 B
//             = 2026-11-17 Steam 自动更新后的版本（单人战役跑的就是它）
//   Old build  md5 68278cc0c3a1e23d96c2b9d722ae7670   9,509,376 B
//             = the copy used by the F:/BMServer deathmatch server (standalone install, not updated by Steam)
//   New build  md5 421fee309fdc22f3dc7b5207a4810c3e   9,530,984 B
//             = the version after the 2026-11-17 Steam auto-update (this is what the single-player campaign runs)
// 两版的 IsMultiplayer 分支结构完全一致，只是地址随代码增长上移，因此本文件
// **不需要按版本分支** —— 签名自己会落到正确位置。下面注释里的地址写成
// 「新 build（旧 build）」；只有一处地址两版相同时会注明“两版一致”。
// The IsMultiplayer branch structure is fully identical in both builds; only the addresses shift up as code grows, so this file
// **does not need per-version branching** — the signature lands at the correct location by itself. Addresses in the comments below are written as
// "new build (old build)"; the one address that is the same in both builds is noted as "same in both builds".
//
// BM 的 tau 用两处 IsMultiplayer 分支区分单人/多人
// （[g_pGameRules]->vtable+0x88，vtable 字节偏移 0x88 = 索引 34，两版一致）：
// BM's tau uses two IsMultiplayer branches to distinguish single-player/multiplayer
// ([g_pGameRules]->vtable+0x88; vtable byte offset 0x88 = index 34, same in both builds):
//
//  1. CWeapon_Tau::FireBeam @ 0x1048DDA0（旧 0x1048C780），je @ 0x1048DEF8（旧 0x1048C8D8）
//  1. CWeapon_Tau::FireBeam @ 0x1048DDA0 (old 0x1048C780), je @ 0x1048DEF8 (old 0x1048C8D8)
//         0F 84 DE 00 00 00    je 0x1048DFDC（旧 0x1048C9BC） ← 单人路径
//     单人路径（0x1048DFDC）算完击退的 X/Y 分量后，在 0x1048E038（旧 0x1048CA18）执行
//     The single-player path (0x1048DFDC), after computing the X/Y components of the knockback, executes at 0x1048E038 (old 0x1048CA18)
//         mov dword ptr [ebp-0x18], 0
//     把击退向量的 **Z 分量清零** → 单人没有向上推力，即没有高斯跳。
//     clearing the **Z component** of the knockback vector → single-player has no upward push, i.e. no gauss jump.
//     多人路径（紧跟 je 的 0x1048DEFE = 旧 0x1048C8DE）三轴都算：
//     0x1048DF4D / 0x1048DF5B / 0x1048DF72 依次读返回向量的 [eax]/[eax+4]/[eax+8]
//     （旧对应 0x1048C955 附近读 Z），0x1048DFD5（旧 0x1048C9B5）写回 [ebp-0x18]
//     → 有高斯跳。
//     两条路都在 0x1048E05B（旧 0x1048CA3B）合流，用同一个 ConVar 缩放（X/Y 也同样缩放，
//     所以单人的水平击退是有的，缺的只有垂直分量），随后 call 0x1011D8D0（旧 0x1011D7E0）。
//     The multiplayer path (0x1048DEFE = old 0x1048C8DE, immediately after the je) computes all three axes:
//     0x1048DF4D / 0x1048DF5B / 0x1048DF72 read the returned vector's [eax]/[eax+4]/[eax+8] in order
//     (old: reads Z around 0x1048C955), and 0x1048DFD5 (old 0x1048C9B5) writes it back to [ebp-0x18]
//     → gauss jump is available.
//     Both paths merge at 0x1048E05B (old 0x1048CA3B) and are scaled by the same ConVar (X/Y are scaled too,
//     so single-player does have horizontal knockback; only the vertical component is missing), then call 0x1011D8D0 (old 0x1011D7E0).
//
//  2. CWeapon_Tau::ChargeFire @ 0x1048ED00（旧 0x1048D6E0），je @ 0x1048EE60（旧 0x1048D840）
//  2. CWeapon_Tau::ChargeFire @ 0x1048ED00 (old 0x1048D6E0), je @ 0x1048EE60 (old 0x1048D840)
//         74 37                je 0x1048EE99（旧 0x1048D879）
//     ← 单人路径：副攻冷却 = curtime + 开火动画时长
//     紧随其后的 0x1048EE62（旧 0x1048D842）是多人路径：
//     SendWeaponAnim(0xB5) + call 0x10491270（旧 0x1048FC50，副攻冷却 = curtime）
//     → 立即可再射。
//     ← single-player path: secondary-attack cooldown = curtime + fire animation duration
//     Immediately after it, 0x1048EE62 (old 0x1048D842) is the multiplayer path:
//     SendWeaponAnim(0xB5) + call 0x10491270 (old 0x1048FC50, secondary-attack cooldown = curtime)
//     → can fire again immediately.
//
// 插件用 GameConfGetAddress 取到这两条 je 指令的运行时地址，校验首字节后在内存里
// 把它们抹成 NOP（只改内存，不动磁盘文件、不动 cfg），于是引擎在这两处永远走多人分支。
// 行为 = 引擎自己的多人代码路径，不是重写的物理/冷却近似值。
// The plugin uses GameConfGetAddress to obtain the runtime addresses of these two je instructions; after validating the first byte it patches them
// to NOP in memory (memory only; disk files and cfg are untouched), so the engine always takes the multiplayer branch at these two points.
// Behaviour = the engine's own multiplayer code path, not a reimplemented physics/cooldown approximation.
//
// ---------------------------------------------------------------------------
// 签名必须「抗重定位」—— 这是 v1.1.0 高斯跳没生效的原因，务必记住：
// Signatures must be "relocation-safe" — this is why the v1.1.0 gauss jump did not work; be sure to remember it:
//
// SourceMod 的 GameConfGetAddress 是在**进程内存**里扫描已加载的模块，而绝对地址类
// 指令（mov ecx,[abs] / cmp reg,imm32 / movss xmm,[abs]）的 32 位字段在加载时会被
// 基址重定位改写。只在磁盘文件上验证唯一命中是不够的 —— 签名一旦跨进这种字段，
// 磁盘上命中、运行时必然失配（日志表现为 "cannot find <key>"）。
// SourceMod's GameConfGetAddress scans loaded modules in **process memory**, and the 32-bit fields of absolute-address
// instructions (mov ecx,[abs] / cmp reg,imm32 / movss xmm,[abs]) are rewritten at load time by
// base relocation. Verifying a unique match on the disk file alone is not enough — once a signature spans such a field,
// it matches on disk but necessarily mismatches at runtime (the log shows "cannot find <key>").
//
// FireBeam 那条 je 之后紧跟 `cmp ecx, <ConVar 静态对象>`（新 build 0x110FB5E0 /
// 旧 build 0x110FA098），该 imm32 有重定位项（新 0x1048DF00 / 旧 0x1048C8E0）；
// 所以整条 imm32 用 \x2A 通配，只保留与重定位无关的字节（寄存器/短立即数/相对位移）。
// The je in FireBeam is immediately followed by `cmp ecx, <ConVar static object>` (new build 0x110FB5E0 /
// old build 0x110FA098); that imm32 has a relocation entry (new 0x1048DF00 / old 0x1048C8E0);
// so the whole imm32 is wildcarded with \x2A, keeping only bytes unrelated to relocation (registers/short immediates/relative displacements).
//
// 验证手段：smx_analysis/sig_check.py —— 它把 PE 的 base relocation 表施加到文件字节上，
// 模拟任意 ASLR 基址后再扫描，结果与运行时一致（已用它复现了 v1.1.0 的失配与本次的命中）。
// Verification method: smx_analysis/sig_check.py — it applies the PE base relocation table to the file bytes,
// simulates an arbitrary ASLR base address, then scans; the result matches runtime (it was used to reproduce both the v1.1.0 mismatch and this match).
//   python sig_check.py <server.dll> "<pattern>"
// 要求：磁盘镜像与加载镜像都只有 1 处命中，且地址就是上面注释的 je。
// 2026-11-17 复核：两版 build 都满足（新 0x1048DEF8 / 0x1048EE60，
// 旧 0x1048C8D8 / 0x1048D840），故签名字符串一个字节都不用改。
// Requirement: exactly one match in both the disk image and the loaded image, and the address must be the je noted in the comments above.
// Rechecked on 2026-11-17: both builds satisfy this (new 0x1048DEF8 / 0x1048EE60,
// old 0x1048C8D8 / 0x1048D840), so not a single byte of the signature strings needs changing.
// ---------------------------------------------------------------------------
